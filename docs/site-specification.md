# 高専祭 Web サイト 仕様書・要件定義書 2026

最終更新: 2026-06-28  
作成方針: 本書は 2026 年度版の高専祭 Web サイト仕様書です。2026 年度で採用する CMS 内製化、Better Auth、SQLite + Drizzle、記事機能拡張、当日運営向け更新機能の方針を記載します。

## 1. システム概要

### 1.1 目的

高専祭の来場者向けに、必要な情報を一元的に提供する。

- 開催概要
- お知らせ一覧と詳細
- 校内マップ
- 屋台などの企画情報
- イベントタイムテーブル
- 運営向け CMS によるコンテンツ管理
- お知らせとブログ記事の発信
- イベントの当日変更反映
- 屋台情報とリアクションの表示

### 1.2 システム構成

- フロントエンド: Next.js App Router
- API: Hono
- CMS: API と同一基盤上で内製実装する管理画面
- 認証: Better Auth
- データベース: SQLite + Drizzle
- UI/アニメーション:
  - Tailwind CSS
  - ダイアログ UI ライブラリ
  - アニメーションライブラリ
  - スライダーライブラリ
  - ズーム・パン操作ライブラリ

### 1.3 実行構成

- モノレポ構成を前提とする
- フロントエンドと API は別プロセスで起動する
- 公開サイトと運営 CMS は同一リポジトリ内で管理する
- ルートワークスペースから一括起動できる構成とする
- ポート番号や起動方法は環境に応じて変更可能とする
- ブログページも公式サイトと同居させる

## 2. 技術要件

### 2.1 基本方針

- フロントエンドは型安全に API を利用できる構成とする
- CMS は外部 SaaS ではなく、既存 API と既存 DB を利用して内製する
- 認証が必要な運営機能は Better Auth で保護する
- CMS 由来の本文はサニタイズして表示する
- お知らせ、ブログ、マップ、イベント、会場、屋台情報を SQLite + Drizzle で管理する
- ページ単位だけでなく、セクション単位でも再利用しやすいコンポーネント分割を行う
- 記事は「重要なお知らせ」と「ブログ系記事」を近い運用で管理できるようにする
- ブログ記事には画像と動画を添付できるようにする
- 記事および屋台にはリアクションを付与できるようにする
- トップページの固定セクションデータは DB・API の管理対象外とし、静的データまたはファイル管理とする
- 内部主キーとは別に、必要なデータは stable な運用IDを持てるようにする
- 公開 URL は専用 `slug` を持たず、必要に応じて `code` または `id` をそのまま使う

### 2.2 環境変数

#### API 側

- フロントエンドの許可オリジン
- Better Auth のシークレット
- Better Auth で使用する認証関連設定
- SQLite ファイルパスまたは DB 接続設定
- アップロードファイル保存先パス

#### フロント側

- API ベース URL

### 2.3 認証要件

- 一般公開ページは認証不要で閲覧できる
- 認証対象は CMS、ブログの CUD、イベント情報の CUD とする
- フロントエンド、API ともに認証対象機能のみに認証を付与する
- ユーザー管理、セッション管理、ログイン状態管理は Better Auth を利用する
- ログイン方式はユーザー名 + パスワードとする
- 初期ユーザーは手動投入する
- 以降のユーザー管理は管理者権限を持つユーザーがフロントエンド経由で行う
- 権限は `shop_staff` `committee` `admin` の 3 段階とする
- `shop_staff` はブログ投稿のみ可能とする
- `committee` は `shop_staff` の権限に加え、お知らせ投稿とイベント情報変更を可能とする
- `admin` は `committee` の権限に加え、ユーザーなどのデータの管理を可能とする

### 2.4 データ永続化要件

- 既存の SQLite + Drizzle を継続利用する
- 記事、ユーザー、セッション、タグ、会場、イベント変更情報、屋台情報、リアクションを同一 DB で管理する
- 屋台詳細モーダルで表示するメニューと価格は静的データであっても DB に格納する
- 画像・動画ファイルはレンタルサーバー上のローカルストレージに保存し、DB ではパスを管理する
- 外部参照やデータ再投入に備え、会場、イベント、屋台、屋台メニュー、マップ関連は内部主キーとは別に運用IDを持てるようにする

### 2.5 対応ブラウザ

- iPhone Safari
- Safari
- **Firefox**
- Chrome
- Edge

## 4. 共通仕様

### 4.1 レイアウト共通

- 全ページで統一レイアウトを適用する
- メタデータ、OGP、フォント、背景表現はサイト全体で統一する
- 初回表示時の演出有無は遷移元に応じて切り替えられる構成とする
- CMS 管理画面は公開サイトと責務を分け、必要に応じて別レイアウトを適用する

### 4.2 外部流入判定

- 同一オリジン遷移か外部流入かを判定する
- 判定結果に応じて以下を切り替える
  - 初回ロード演出
  - ヒーロー演出の開始タイミング
  - マップの自動スクロール挙動

### 4.3 ナビゲーション

- 主要ページでは固定ナビゲーションを表示する
- 最低限、トップ、お知らせ、マップ、イベントへの導線を持つ
- モバイル・デスクトップの両方で操作しやすい配置にする

### 4.4 デザイン方針

- 学園祭らしい視認性と賑やかさを両立させる
- 背景、パネル、文字色、アクセントカラーは全体でトーンを統一する
- ページごとに雰囲気を変えつつも、共通 UI として認識できる見た目を維持する

### 4.5 共通インタラクション

- セクションの表示時にアニメーションを入れる
- タイトルやカードなどにスクロール連動演出を持たせる
- 過剰な演出で可読性や操作性を損なわないことを優先する

## 5. トップページ仕様 `/`

### 5.1 ページ全体構成

トップページは以下のセクションで構成する。

1. ヒーロー
2. 挨拶または導入メッセージ
3. トップ NEWS
4. 企画紹介
5. 注意事項
6. アクセス
7. 協賛
8. パンフレット

### 5.2 データ方針

- ヒーロー、挨拶、注意事項、アクセス、協賛、パンフレットの固定文言や画像は DB・API の管理対象外とする
- これらの文言、画像、リンクは静的データまたはファイル管理で扱う
- トップ NEWS と企画紹介に使うお知らせ・屋台情報は公開 API / DB 管理対象とする

### 5.3 トップ NEWS セクション

- API からお知らせ一覧を取得して表示する
- 表示項目は公開日、タグ、タイトルを基本とする
- 各項目からお知らせ詳細へ遷移できる
- 一覧ページへの導線を設ける

異常時の扱い:

- エラーメッセージを表示する
- データ未登録時は空状態 UI を表示する

### 5.4 企画紹介セクション

- 屋台や注目企画を視覚的に紹介する
- PC とモバイルで最適な UI を切り替える
- 選択中の企画について、タイトル、説明、画像、マップ導線を表示する
- 屋台詳細モーダルでは以下を表示する
  - 企画名
  - 説明
  - ポスター画像
  - メニュー一覧
  - 価格
  - SNS リンク
  - リアクション UI
  - マップ導線
- 屋台情報、メニュー、価格は DB で管理する
- 場所は専用セクションを設けず、説明欄とマップ上の位置で案内する
- 屋台画像は 1 件につき 1 枚とする
- 屋台の並び順は `sortOrder` で管理する
- 屋台メニューの当日変更は行わない前提とする

### 5.5 注意事項セクション

- 来場者向けの注意事項を掲載する
- 注意事項は 2026 年度運営方針に基づいて管理する

### 5.6 アクセスセクション

- 会場住所
- 地図埋め込み
- 公共交通機関案内
- シャトルバス案内
- 雨天時や交通変更時の補足

### 5.7 協賛セクション

- 協賛情報を一覧表示する
- ロゴ画像、名称、リンク有無に対応する

### 5.8 パンフレットセクション

- パンフレット画像のプレビューを表示する
- PDF ダウンロード導線を設ける

## 6. お知らせ一覧仕様 `/news`

### 6.1 ページ目的

運営からの重要なお知らせを時系列で一覧表示し、詳細ページへ誘導する。

### 6.2 表示内容

- ページ見出し
- 公開日
- タグ
- タイトル
- 重要度
- トップページへの導線

### 6.3 データ取得

- API 経由でお知らせ一覧を取得する
- 必要に応じて最新順で表示する
- 再検証間隔やキャッシュ方針は運用要件に応じて調整する

### 6.4 例外時

- API エラー時はエラー表示を行う
- データが 0 件の場合は空状態 UI を表示する

## 7. お知らせ詳細仕様 `/news/[id]`

### 7.1 ページ目的

1 件のお知らせ本文を表示する。

### 7.2 表示内容

- タイトル
- 公開日
- タグ
- 本文
- 一覧に戻る導線

### 7.3 メタデータ生成

- 記事タイトルを用いた `<title>` を生成する
- 本文要約をもとに description を生成する

### 7.4 エラー時

- 記事未存在時は未検出メッセージを表示する
- API エラー時は状態に応じたエラー文を表示する

### 7.5 お知らせデータ方針

- お知らせは速報性と重要度を重視する
- 公開状態、公開日時、重要度、タグを持てるようにする
- 重要度は `high` `medium` の 2 段階とする
- トップページの並び順は `publishedAt desc` とするが、重要度`high`のものは上位に表示する
- 重要度は公開後に変更できるものとする
- ピン留め機能は持たない
- 重要度バッジは表示しない
- 本文内画像の添付に対応する

## 8. ブログ仕様 `/blog`

### 8.1 ページ目的

高専祭に関連する読み物系コンテンツを一覧表示し、各詳細ページへ誘導する。

### 8.2 記事種別

- 各屋台のおすすめ商品紹介
- 実行委員会による商品レビュー
- 企画の見どころ紹介
- 運営裏話や準備レポート

### 8.3 表示内容

- アイキャッチ画像
- 本文内画像
- 本文内動画
- タイトル
- 概要
- 公開日
- タグ
- 執筆者名または表示用名義
- リアクション数
- サムネイル画像は任意とし、未設定時の表示崩れがないようにする

### 8.4 一覧ページ要件

- 新着順で記事を表示する
- 並び順は `publishedAt desc` とする
- 検索を実装する
- タグ、記事種別で絞り込みできるようにする
- お知らせ一覧とは別導線で運用する

### 8.5 詳細ページ要件 `/blog/[id]`

- タイトル
- アイキャッチ画像
- 本文
- 添付画像
- 添付動画
- 公開日
- 執筆者
- タグ
- リアクション UI
- タグ導線
- 関連記事表示は行わない
- 動画はアップロード動画を表示対象とする
- 動画は先読みしない

### 8.6 記事データ方針

- お知らせとブログ記事は共通のコンテンツ基盤で管理する
- 記事種別を表すフィールドを持ち、公開側で表示先を分ける
- `news` は重要なお知らせ向け、`blog` は読み物向けとして扱う
- `news` と `blog` は別テーブルで管理する
- 画像と動画の添付情報を保持する
- 記事ごとにリアクション集計を保持する
- ブログ記事詳細 URL は `id` をそのまま使う
- 予約投稿に対応する
- 執筆者表示名は未定のため検討事項とする

## 9. 校内マップ仕様 `/map`

### 9.1 ページ目的

来場者が企画位置や各種案内ポイントを視覚的に確認できるようにする。

### 9.2 ページ構成

1. 固定ナビ
2. 企画を探す導線
3. 企画選択用メニュー
4. 補足案内カード
5. 複数階層または複数エリアのマップ

### 9.3 マップデータ方針

- 校外、屋外、校舎階層ごとにマップを分ける
- マップ画像と構成は昨年度データを参照する
- 企画ピン、案内ピン、ラベルを別データとして管理する
- 各ピンは座標、表示名、色、補足情報を持てるようにする
- 座標、画像、屋台参照情報は DB または専用データテーブルで管理する
- `index` パラメータは引き続き使用する
- 静的ピンとラベルも DB で管理する
- 1 屋台に複数ピンが紐づく可能性を許容する

### 9.4 スライドメニュー

- 企画一覧から目的の企画を選択できる
- 画面サイズに応じて表示方向を切り替える
- 選択時は対象企画のマップへ移動する

### 9.5 URL パラメータ仕様

- `index`: 企画データ配列上の参照位置
- 遷移元を示す補助パラメータを必要に応じて持てるようにする

挙動:

- 対象企画のあるマップまで自動スクロールする
- 対象ピンを強調表示する
- モーダルやメニューの初期表示を遷移元に応じて切り替える

### 9.6 マップ表示仕様

- ベース画像を表示する
- 拡大縮小とパン操作に対応する
- 現在選択中の企画や対象マップを視覚的に強調する

### 9.7 ピン仕様

#### 企画ピン

- 企画番号または識別子を表示できる
- 選択中企画は強調表示する
- クリックまたはタップで詳細モーダルを開けるようにする
- 屋台に紐づくピンでは屋台詳細モーダルを開く

#### 静的ピン

- 受付
- 休憩所
- ゴミ箱
- 企業ブース
- バス乗降場所

#### 補助機能

- マップ URL をコピーできるようにする
- 特定ピンに時刻表や補足情報モーダルを紐付けられるようにする
- 屋台詳細モーダルからリアクションを送信できるようにする
- リアクションはハートアイコン固定とする

### 9.8 時刻表モーダル

- バスなど時刻依存の案内を表示する
- 次便までの残り時間を計算できる
- 運行終了後の表示に対応する
- 次便の強調表示を行う

時刻表データは 2026 年度運行情報として管理し、機械可読な出発時刻を持つ。

## 10. イベント一覧仕様 `/events`

### 10.1 ページ目的

日別、会場別の順でタイムテーブルを一覧表示し、詳細ページへ誘導する。

### 10.2 表示内容

- 会場名
- 日付
- 開始時刻と終了時刻
- 企画名
- 注意事項
- 開催状態
- 当日変更表示

### 10.3 データ方針

- ステージ、公演、展示などを統一フォーマットで扱えるようにする
- 雨天時の代替会場や参加制限などの補足情報を持てるようにする
- 各イベントは通常情報とは別に当日変更情報を持てるようにする
- 当日変更には `中止` `時間変更` `会場変更` `備考追加` を含める
- 開催状態は `scheduled` `changed` `cancelled` を使用する
- 当日変更履歴は保持せず最新状態のみを管理する
- データ更新後は即時公開する
- 変更終了後に元の表示へ戻す処理は持たない
- 中止イベントは一覧から消さず表示する
- 会場変更で選べる会場は事前登録済み会場に限る

### 10.4 当日変更 UI

- 実行委員が CMS からイベントの当日変更を入力できるようにする
- CMS の当日変更 UI はイベント一覧ベースで入力できるようにする
- 入力項目:
  - 変更種別
  - 変更後開始時刻
  - 変更後終了時刻
  - 変更後会場
  - 補足メッセージ
- 公開側 UI ではイベント一覧とイベント詳細の両方で変更内容を目立つ形で表示する
- 中止時は通常スケジュールよりも優先して `中止` 表示を行う
- 表示色は `中止 = 赤` `変更 = 黄` とする

## 11. イベント詳細仕様 `/events/[code]`

### 11.1 目的

特定イベントの詳細説明を表示する。

### 11.2 表示仕様

- 一覧へ戻る導線を表示する
- 出演時間、会場、補足情報を表示する
- 1 code = 1 event とする
- 対象が存在しない場合は未検出メッセージを表示する
- 当日変更がある場合は詳細ページでも変更前情報を併記する

### 11.3 URL 識別子方針

- イベント詳細 URL は `events.code` をそのまま使う
- `code` はテーブル内で一意とし、表示名とは分離して管理する

## 12. CMS 管理機能仕様 `/cms`

### 12.1 目的

運営メンバーが公開サイト用コンテンツをブラウザ上で管理できるようにする。

### 12.2 管理対象

- お知らせ
- ブログ記事
- イベント
- 会場
- 屋台情報
- リアクション集計
- ユーザー
- タグ
- マップ関連データ

### 12.3 主要機能

- ログイン
- ログアウト
- 記事一覧表示
- 記事作成
- 記事編集
- 下書き保存
- 予約投稿
- 公開状態切り替え
- 削除
- イベント当日変更入力
- 屋台情報編集
- 会場管理
- リアクション集計閲覧
- ユーザー管理
- タグ管理
- プレビュー

### 12.4 認可方針

- Better Auth による認証を使用する
- 権限に応じて編集可能範囲を制御する
- 実行委員はイベント当日変更を更新できるようにする
- 屋台情報編集は管理者のみ可能とする

### 12.5 エディタ要件

- タイトル、本文、概要、アイキャッチ画像、タグ、記事種別を編集できる
- 記事には画像と動画を添付できる
- 公開日時の指定に対応する
- 本文はリッチテキストまたは Markdown 相当で編集する
- GUI で編集できる Markdown エディタを採用する
- 画像アップロードはドラッグアンドドロップに対応することが望ましい
- 動画アップロードは進捗表示に対応する
- イベント変更入力 UI は通常編集画面とは分け、当日運営で素早く更新できる構成とする
- CMS はスマートフォンからの投稿操作に対応する
- 削除は論理削除とする

## 13. API 仕様

### 13.1 API 基本

- ベース URL は環境変数で切り替え可能とする
- 公開 API と CMS API は責務を分離する

## 14. 2026 データ管理方針

- お知らせ、ブログ記事、イベント、屋台、屋台メニュー、リアクション、認証関連データは SQLite + Drizzle で管理する
- `news` と `blog` は別テーブルで管理する
- 屋台メニューと価格は静的運用であっても DB 登録とし、公開側は API 経由で取得する
- イベントの通常情報と当日変更情報は分けて管理し、公開時は当日変更情報を優先表示する
- ブログの画像・動画添付情報は記事本体と関連付けて管理する
- タグはマスタテーブルで管理する
- 会場はマスタテーブルで管理する
- 屋台表示順は `sortOrder` で管理する
- 屋台とマップピンは 1 対多を許容する
- トップページの固定セクションデータは DB 管理対象外とする
- 会場、イベント、屋台、屋台メニュー、マップ関連は stable な運用IDを `unique` で持つ

## 15. 非機能要件

### 16.1 運用性

- 2026 年度運用で CMS から更新する対象を明確にする
- コンテンツ更新だけで済む箇所と、実装変更が必要な箇所を分離する
- CMS から変更できる範囲を増やし、コード修正なしで運営できる領域を広げる
- 当日運営で必要な更新を数手で反映できる UI を優先する
- 初期投入データは管理者ユーザーが CMS 経由で投入する
- 当日変更の更新担当者は実行委員 5 人程度と管理者を想定する
- SQLite データのバックアップを行う

### 16.2 保守性

- 画面、データ、API、UI 部品を分離しやすい構成にする
- 固定データの肥大化を避け、必要に応じてファイル分割する
- SQLite のスキーマ変更は Drizzle の migration で管理する
- 認証基盤は Better Auth に集約し、独自認証ロジックの分散を避ける
- 屋台メニューやリアクションのような公開機能追加に備え、記事系と企画系のテーブルを分離して保守しやすくする

### 16.3 利用性

- スマートフォンでの閲覧を優先する
- キーボード操作に対応する
- 地図、時刻表、企画詳細など、当日利用の多い情報へ短い導線で到達できることを重視する
- お知らせとブログの導線を分け、速報性の高い情報と読み物系情報を混同しない
- 屋台詳細モーダル内でメニュー、価格、リアクションまで完結して閲覧できるようにする
- ブログ動画は通信量に配慮し、表示時にのみ読み込む

## 16. 検討事項

- 執筆者表示名をユーザー名と分離するか
- 動画アップロードの上限サイズと許可形式
- ページネーション件数
- 検索 API の詳細仕様
